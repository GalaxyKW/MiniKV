# 性能基线：从数据解释等待

[返回 README](../README.md) · [重跑实验](benchmark-experiments.md) · [指标口径](observability.md)

这份记录使用提交 `7c488b7` 的实际运行结果，展示如何从吞吐量、尾延迟和内部等待判断下一步实验。两种持久化模式的成功确认语义不同，应分别比较。这里的数据来自同机客户端和服务端、小数据集、闭环请求与 NTFS3 文件系统，不能当作其他硬件、文件系统或外部到达速率下的容量承诺。

## 环境与负载

| 项目 | 本次配置 |
| --- | --- |
| CPU | Intel Xeon E3-1270 v3 @ 3.50 GHz；8 个可用逻辑 CPU |
| 可见内存 | 约 15.6 GiB；首批实验前可用约 2.25 GiB，未清空系统缓存 |
| 系统与数据盘 | Linux 6.8.0-139-generic；`/dev/nvme0n1p2`，NTFS3 |
| 构建 | C++ `RelWithDebInfo`（`-O2 -g -DNDEBUG`）；Go 1.22.0；未开启 sanitizer |
| 进程 | 客户端、Go 网关、C++ 引擎共用主机；两个 Go 进程均 `GOMAXPROCS=4` |
| 负载 | 每轮 100,000 请求、40 个闭环 worker；5,000 key；128 字节 value；seed 1 |
| 操作 | mixed 20% PUT / 5% DELETE / 其余 GET；先预置全部 key，预置不计入测量 |
| 引擎与网关 | 20 个数据线程；RPC 池 64；请求队列 128；WAL 队列 16 MiB |
| WAL 与快照 | batch 64、flush 2 ms；分别关闭自动快照或间隔 1,000 ms |
| 采样与重复 | 资源 100 ms、状态 250 ms；每种配置 3 轮，轮换执行顺序，每轮新数据目录 |

负载生成器为 `indexed-pcg-v1`。所有轮次生成相同的 PUT 19,979、GET 75,087、DELETE 4,934 个测量请求；并发到达顺序与命中率仍可能不同。首批采集时工作区干净；第二批记录了工具、文档与测试改动，但运行的是首批保存的相同执行文件。24 份客户端报告均标记 VCS 版本 `7c488b7`、`vcs_modified=false`。C++ 二进制摘要、当前源码状态和 CMake 配置分别保留，不把这些记录当作独立的构建来源证明。

主机还有其他工作负载，实验前 loadavg 约为 8，没有停止其他进程或更改调度、CPU 频率与缓存配置。这个单次主机观测不代表整个实验期间的负载轨迹；内部进程资源样本也不能完整解释设备和操作系统的等待。

## 原始记录与复查

[原始归档目录](../benmark/baselines/2026-09-14-7c488b7/)包含开启和关闭周期采样的两批实验，各 12 轮。[MANIFEST.json](../benmark/baselines/2026-09-14-7c488b7/MANIFEST.json) 记录归档大小、文件数和 SHA-256；归档保留原始命令、报告、状态、资源、日志与主机背景，省略实际执行文件和生成的数据文件。没有筛除慢轮次。

从仓库根目录校验、解压并重新汇总：

```sh
(cd benmark/baselines/2026-09-14-7c488b7 && sha256sum -c SHA256SUMS)
baseline_extract_dir="$(mktemp -d)"
tar -xzf benmark/baselines/2026-09-14-7c488b7/sampled.tar.gz -C "$baseline_extract_dir"
tar -xzf benmark/baselines/2026-09-14-7c488b7/unsampled.tar.gz -C "$baseline_extract_dir"
python3 benmark/summarize.py "$baseline_extract_dir/sampled" "$baseline_extract_dir/unsampled"
```

便携归档没有执行文件副本，汇总会明确显示 `recorded_hashes_only`；这不等于重新核验过二进制。两批实验实际运行时使用相同的已保存二进制，三份 SHA-256 完全一致。原始路径只记录当时环境，解压位置可以不同。

要运行相同配置，先在对应提交的独立工作树构建，再启动实验：

```sh
git worktree add --detach /tmp/minikv-baseline-7c488b7 7c488b7
cd /tmp/minikv-baseline-7c488b7
make JOBS=4
python3 benmark/experiment.py \
  --requests 100000 --workers 40 --keyspace 5000 --repeats 3 \
  --engine-workers 20 --rpc-pool 64 --gomaxprocs 4 \
  --wal-batch 64 --wal-flush-ms 2 --snapshot-ms 1000 \
  --sample-ms 100 --stats-ms 250 --run-timeout 600
```

路径必须尚不存在；原始数据盘为 NTFS3，临时工作树所在文件系统可能不同。重跑时将 `--output` 指向要评估的数据盘上的新目录，并记录硬件、文件系统和主机负载。仅复用命令并不能复现原机器的吞吐量。

## 开启周期采样的三次重复

以下每个单元格为**轮次中位数 [最小值，最大值]**。P99 列汇总的是每轮 P99，不能理解为将全部请求合并后的 P99。

| WAL 模式 | 自动快照 | 成功 QPS | 每轮 P99，ms |
| --- | --- | ---: | ---: |
| throughput | 关闭 | 32,011 [30,597，32,204] | 2.505 [2.421，2.997] |
| throughput | 1,000 ms | 31,422 [29,913，31,975] | 2.595 [2.549，2.826] |
| reliable | 关闭 | 5,132 [4,920，5,141] | 10.023 [10.022，15.523] |
| reliable | 1,000 ms | 5,100 [5,097，5,110] | 11.129 [11.115，11.220] |

12 轮均完成全部测量请求，系统失败为 0。开启快照的 6 轮都在测量区间内观察到了快照活动。throughput 的测量阶段约 3 秒，reliable 约 20 秒，因此相同快照间隔下，两种模式经历的快照次数不同。

在这个较小的数据集和有限重复次数下，快照开启与关闭的吞吐量范围接近，可靠模式尾延迟又存在离群轮。现有结果不足以断言快照代价可忽略，也不足以给出稳定的性能损失百分比。扩大数据集、延长运行和增加重复，才能进一步评估状态复制、额外内存与 WAL 后缀回收的成本。

## 关闭周期采样的对照

第二批只将 `--sample-ms` 和 `--stats-ms` 改为 0，仍保留必要的启动、结束与排空状态检查。下面同样是三轮的中位数和范围：

| WAL 模式 | 自动快照 | 成功 QPS | 每轮 P99，ms |
| --- | --- | ---: | ---: |
| throughput | 关闭 | 32,916 [32,587，33,041] | 2.405 [2.356，2.409] |
| throughput | 1,000 ms | 32,335 [32,302，33,413] | 2.440 [2.318，2.473] |
| reliable | 关闭 | 5,110 [5,101，5,111] | 10.170 [10.155，10.223] |
| reliable | 1,000 ms | 5,063 [5,007，5,085] | 11.538 [11.209，12.554] |

该批 12 轮也全部完成、系统失败为 0。throughput 结果略高，可靠模式没有呈现一致改善。这两批按时间先后运行，未交错采样开关，也没有控制其他主机负载，**不能把差值全部归为采样开销**。后续需要交错或 A/B/A 对照，才有更强的归因依据。

关闭周期采样后，没有测量期 RSS 或内部提交周期数据；也无法用测量期样本确认快照活动，汇总会显示证据不足。预置前与结束后的快照计数差包含预置阶段，不能替代测量窗口内的观测。这批数据用于检查客户端结果对采样开关的敏感性，不用于得出快照成本结论。

## 可靠模式在等待什么

状态分析只使用查询起止时间都落在客户端测量区间内的样本，排除预置和跨边界查询。累计量取首尾样本之差，资源计数使用同一 PID 和启动时间的样本。队列与使用量的均值是样本算术均值，未经时间加权；它们是近似窗口统计，不是逐请求 trace。

首轮 reliable、快照关闭时：

- 已结束 WAL 提交平均约 2.407 ms，提交周期近似值约 4.510 ms；两者之差约 2.102 ms。
- 每次提交对应的写记录近似值为 5.77，远低于 batch 64。
- 活跃数据线程样本均值为 19.09/20，数据队列均值为 15.76，采样最大为 20。
- RPC 连接池使用量采样最大为 40/64，名额等待平均约 0.98 μs；没有 RPC 错误、重试或数据任务入队拒绝。

提交周期近似值使用首末状态查询结束时间之差除以已结束提交数；本例为 19.242525 秒 / 4,267 次。窗口边界的在途提交和请求仍可能造成小的计数与耗时错位。

这些样本与代码机制一致：可靠写入等待自己的 WAL 序列持久化，可靠 GET 等待读取时观察到的全局序列持久化，等待期间都占用数据线程。20 个线程无法通过普通可靠请求积累到 64 条未确认写入，后台主要等待刷新时刻；完成一次提交后，又重新设置“当前时间 + 2 ms”的刷新时刻。

因此，当前有证据支持的解释是：可靠确认等待占住工作线程，进而形成数据任务排队。增加 RPC 池容量没有对应的瓶颈证据。

WAL 提交计时包含逐条 write、最后一次 `fdatasync` 及期间的调度延迟，**不是 `fdatasync` 的单独耗时**。它不包含等待 I/O 锁、后台刷新时刻和提交结束后获取状态锁的时间；“提交周期减提交耗时”也不能直接当作精确的定时器等待时间。

## 如何处理离群轮

`r02-reliable-snapshot-off` 的 P99 为 15.523 ms，同组其他两轮约为 10.022 ms。这一轮关闭自动快照，不能把它归因于快照。

其测量窗口中，曾采到最后一次提交耗时约 5.972 ms；一个局部采样区间的平均提交耗时约 3.067 ms，RPC 收发均值也升到约 8.944 ms。数据说明局部路径确实变慢，但没有逐请求延迟时间序列，无法把这些样本与 P99 请求一一对应，也无法进一步区分文件系统、设备和调度原因。该轮保留在范围中。

## 后续控制实验

已有的两批对照尚不能精确分离采样开销。机制实验先一次改变一个变量：保持 reliable、其他负载和容量相同，分别比较 flush 1/2 ms、batch 4/64，以及数据线程 40/20。观察提交周期、每批记录数、排队和尾延迟是否随预期机制变化，同时检查是否出现新的 CPU 或 RPC 限制。

这些实验可以先通过已有配置完成。改变默认值或请求调度结构之前，需要重复结果支持，也需要继续保留现有持久化与故障恢复保证。
